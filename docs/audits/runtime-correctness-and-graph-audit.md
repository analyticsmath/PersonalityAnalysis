### Timeout Root Cause

The user-reported error **"Request timed out while waiting for AI processing. Please retry once."** is generated by:

**File:** `frontend/src/api/client.js:43`

```javascript
timeout: 15000,   // line 27 — global default for all requests
// ...
if (error.code === 'ECONNABORTED') {
  return Promise.reject(
    new Error('Request timed out while waiting for AI processing. Please retry once.')  // line 43
  );
}
```

**Root cause:** The default axios client has a **15,000 ms timeout** applied to ALL requests. Requests that have no explicit `timeout` override inherit this 15-second limit. When any request exceeds 15 seconds (including the result fetch, scoring trigger, career chat, or why-not endpoint), axios emits `ECONNABORTED`, and the interceptor wraps it in this single hardcoded message — even for requests with nothing to do with AI.

**Requests that use the default 15-second timeout** (no override in `assessmentFlowApi.js`):

| Function | Endpoint | Likely Duration |
|---|---|---|
| `getActiveFlowSession` | `GET /assessment/session/active` | < 1s usually, but can be slow with scoring |
| `getAdaptiveQuestion` | `GET /assessment/{id}/question` | Fast normally |
| `submitAdaptiveAnswer` | `POST /assessment/{id}/answer` | Up to 20s+ if AI question gen triggers |
| `getAssessmentFlowResult` | `GET /assessment/{id}/result` | **10–60s** if scoring + report running |
| `getCareerRecommendations` | `GET /assessment/{id}/career-recommendations` | 5–15s |
| `askCareerChat` | `POST /assessment/{id}/chat` | **20–55s** (AI-backed) |
| `askWhyNotCareer` | `POST /assessment/{id}/why-not` | 20–55s (AI-backed) |
| `downloadAssessmentFlowPdf` | `GET /assessment/{id}/result/pdf` | Synchronous, fast |

Requests with explicit timeout overrides:

| Function | Timeout |
|---|---|
| `uploadCv` | 120,000 ms |
| `submitManualProfile` | 120,000 ms |
| `startAdaptiveAssessment` | 45,000 ms |
| `generateAiReport` (legacy) | 120,000 ms |

**The single worst case:** `getAssessmentFlowResult` fetches scoring + result. If the backend AI narrative is running (~50s), the client times out at 15s, shows the misleading "AI processing" error, and the user sees a broken result page even though the backend finishes correctly.

### Env Config Mismatch

`.env.example` sets `OPENAI_TIMEOUT_MS=45000`. Code defaults to `55000`. If the env var is absent from a deployment, the effective timeout is 10 seconds longer than documented. Recommendation: align the code defaults to the documented example value.

## 5. Big Five Live vs Final Result Mismatch

### A. Live Preview (During Question Answering)

**File:** `frontend/src/pages/AssessmentFlow/TestPage.js`  
**Lines:** `radarStateRef` initialized at ~196–202; computed live at ~634–676

**Mechanism:**
- `radarStateRef` starts at `{O:50, C:50, E:50, A:50, N:50}`
- For each submitted answer, the trait key is inferred by `toTraitToken(question.traitFocus)` (line 54–69)
- The trait's running average is updated: `newValue = ((previous * count) + currentScore) / (count + 1)`
- `currentScore` is derived from `normalizeAnswerScore(answer)` using the raw answer value

**Key property:** This is a **purely frontend approximation** — it never reads from backend scoring. It is a simple running mean of raw answer scores mapped to traits.

**Why it shows "realistic" values:** Because the user's answers directly drive the running average; values spread naturally across O/C/E/A/N as different questions target different traits.

**Trait label for N:** The live preview uses `N: 'Neuroticism'` (not Emotional Stability). No inversion is applied in the live path. (See `TRAIT_LABELS` at line 41–43.)

### B. Final ResultPage OCEAN Radar

**File:** `frontend/src/pages/AssessmentFlow/ResultPage.js:119` → `normalizeAssessmentResult(result)` → `buildRadarTraits(raw)` in `assessmentResultNormalize.js`

**Phase 3 path (deterministic):**
- Reads `raw.scores?.bigFive` (field `openness`, `conscientiousness`, `extraversion`, `agreeableness`, `emotionalStability`)
- Requires `p3.openness.source === 'deterministic'` (line 21 in `assessmentResultNormalize.js`)
- **Guard:** `hasSufficientGraphData(deterministicTraits, ['O','C','E','A','N'], meta)`
  - `isRealScoreMeta(meta)` must return true — fails if `scoreSource` is `mock`/`unknown`, or `scoreValidity` is `insufficient_data`/`invalid`, or `legacy_unverified` with evidenceCount 0
  - If guard fails → returns `{O:0, C:0, E:0, A:0, N:0}` (all zeros — this is why the user sees "flat" near-zero values, not flat 50% values)

**Trait for N:** `p3.emotionalStability.score` — the backend scoring engine already inverts Neuroticism to Emotional Stability in `bigFiveScoring.service.js`.

**Legacy fallback path** (when Phase 3 `scores.bigFive` absent):
- Reads `raw.trait_scores || raw.traits`
- Applies `N = 100 - N` inversion in frontend (line 40 of `assessmentResultNormalize.js`)

### Root Cause Candidates (Ranked by Confidence)

| Rank | Cause | Confidence | Evidence |
|---|---|---|---|
| 1 | `scoreMeta.scoreValidity` is `insufficient_data` or `scoreSource` is `legacy_unverified` for a short/incomplete run → `hasSufficientGraphData` returns false → zeros | HIGH | `graphDataGuards.js:24`; frequent with short assessments |
| 2 | `scores.bigFive` source field is not `'deterministic'` (e.g. `'phase3'` or missing) → `hasP3` is false → falls to legacy path which may produce near-50 values | MEDIUM | `assessmentResultNormalize.js:21`; Phase 3 scoring uses `source: 'deterministic'` |
| 3 | `meta` object is null (no scoreMeta persisted) → `!meta` path → returns real deterministic scores (this would be correct, not buggy) | LOW | Only an issue if scoreMeta is lost in serialization |
| 4 | Result endpoint returns different shape than expected | LOW | Would need live API response comparison to confirm |

**The mismatch:** Live preview shows realistic values derived from the user's in-progress answers (frontend approximation). Final result shows zeros or near-zero values when `hasSufficientGraphData` returns false (e.g., a short assessment with `scoreValidity: insufficient_data`). These are fundamentally different data sources and will always diverge on short runs.

## 8. Recovery Banner Audit

### Symptom
"Your assessment progress was recovered." appears on every question during active answering.

### Root Cause

**File:** `frontend/src/pages/AssessmentFlow/TestPage.js:724–726, 922–942`

```javascript
// Line 724
const recoveredSessionId = String(assessmentMachine.session?.sessionId || '');
// Line 725 — THIS IS THE BUG
const showRecoveryBanner = Boolean(recoveredSessionId)
  && recoveredSessionId === String(sessionId || '')
  && Number(assessmentMachine.progress?.answeredCount || 0) > 0;
```

**Analysis:**
- `assessmentMachine.session?.sessionId` is **always populated** as long as `useActiveFlowSessionQuery` returns data (it polls continuously while the stage is in `LONG_RUNNING_STAGES`)
- `recoveredSessionId === sessionId` is **always true** on the question page (they always match)
- `answeredCount > 0` becomes **true permanently** after the first answer

**Result:** `showRecoveryBanner` is `true` for the entire remainder of the session after the first answer. It is never reset to `false`.

**Render condition (line 922):** `{showRecoveryBanner || recoveryState !== 'idle' ? (...)` — the banner renders whenever `showRecoveryBanner` is true, showing "Your assessment progress was recovered" (line 932) even though the user never clicked "Recover Session".

**The correct intent:** `showRecoveryBanner` should only be true after the user explicitly triggers `handleRecoverSession()` (which sets `recoveryState === 'recovered'`). The current logic does not require any explicit recovery action.

### Recommended Fix Direction

`showRecoveryBanner` should depend on `recoveryState === 'recovered'` only:

```javascript
// Replace current showRecoveryBanner with:
const showRecoveryBanner = recoveryState === 'recovered';
// Or: only show banner for one render cycle, then dismiss
```

The `assessmentMachine.session` / `answeredCount` check is the wrong signal — it fires on every poll cycle and is not related to a recovery action.

```jsx
</div>
```

`display: grid` without `grid-template-columns` defaults to a single-column grid — cards stack vertically.

Compare: The "Career Matches" section below (line 804) uses class `phase3-career-grid` which is defined in CSS as:

```css
.phase3-career-grid {
  display: grid;
  grid-template-columns: repeat(2, minmax(0, 1fr));
  gap: 16px;
}
```

**Recommended Fix:**
```jsx
<div style={{ display: 'grid', gridTemplateColumns: 'repeat(auto-fit, minmax(280px, 1fr))', gap: 12 }}>
```
Or add a `.career-intel-grid` CSS class with the same definition as `.phase3-career-grid`.

**Risks:** None — layout-only change. `CareerRecommendationCard` renders as a self-contained Card and adapts to its container width.

## 13. Recommended Three-Phase Repair Direction

*(These are suggested repair tracks, not product roadmap phases.)*

### Track A: Data / Scoring / Graph Correctness (Do First)

1. **PDF OCEAN fix:** Change `pdf-report.service.js` and `unified-contracts.service.js` to read `scores.bigFive` for OCEAN values. Fix the falsy guard (`{}` blocks trait_scores fallback).
2. **Insufficient data UX:** Instead of returning `{O:0,...}` zeros from `buildRadarTraits`, return a sentinel so the chart renders an explicit "Insufficient data" state with a re-assessment prompt.
3. **Dashboard history endpoint:** Add `scores.bigFive` to the history endpoint response so the dashboard radar can use the deterministic path.
4. **Legacy result page alignment:** Pass `scoreMeta` to `TraitRadarChart` on the legacy result page; use `normalizeAssessmentResult` for consistent OCEAN normalization.
5. **N trait label consistency:** Align live preview `N` label and inversion with final result output.
6. **Career Intelligence layout:** Add `gridTemplateColumns` to Career Intelligence container div.

### Track B: AI Latency / Report / PDF Runtime Reliability (Do Second)

1. **Fix per-request timeout overrides:** Add explicit timeouts to `getAssessmentFlowResult` (60s), `askCareerChat` (90s), `askWhyNotCareer` (60s), `getCareerRecommendations` (45s) in `assessmentFlowApi.js`.
2. **Fix generic error message:** Replace the single "Request timed out while waiting for AI processing" message in `client.js:43` with a generic "Request took too long. Please retry." Implement context-specific error handling per request type.
3. **Align env config defaults:** Set code default `openaiTimeoutMs` to 45000 to match `.env.example`.
4. **Consider background report generation:** For the AI narrative, consider returning immediately with a `reportStatus: 'generating'` state, then polling for completion — rather than blocking the HTTP response for up to 50 seconds.
5. **Remove double validation:** Remove the redundant `validateReportWithRepair` call in `ai-result-narrative.service.js`.

### Track C: UI Copy / Layout / Polish / E2E Validation (Do Third)

1. **Consent copy:** Replace "version phase8-v1" in `StepCV.jsx` and `ManualProfileForm.jsx` with user-friendly language.
2. **Card subtitle:** Replace "Explainable fit, gaps, and next steps (Phase 4)" with "Career fit, skill gaps, and next steps".
3. **Metric hints:** Remove "deterministic", "Phase 4", "phase8-v1" from all user-visible strings.
4. **AI fallback career guidance:** Rewrite fallback `careerGuidance` strings to remove engineering language.
5. **Recovery banner:** Fix `showRecoveryBanner` to depend only on explicit user recovery action.
6. **Full E2E test runs:** Run complete assessment flows 2–3 times with different profiles in a live environment; verify OCEAN values match between live preview (approximately), final result, dashboard, and PDF.
7. **Live AI smoke tests:** Run `smoke-openai-provider.js` and `smoke-ai-report-generation.js` with the actual production API key to verify model, latency, schema validation, and fallback behavior.
